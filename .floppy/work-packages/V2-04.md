## 3. Continuity Overseer identity

The identifier field is `continuity_overseer_id`.

Canonical value:

`continuity_overseer_id = "CO-" + project_id`

The referenced `project_id` is the existing V2-03 canonical lowercase UUIDv4.

The Continuity Overseer identity is deterministic, project-scoped, immutable
after establishment, independent of provider/model/conversation memory, and
unchanged by Project Orchestrator succession.

An existing project with a valid committed V2-04 identity preserves that
identity exactly.

Role existence grants no implementation authority, repository-writer
authority, migration authority, integration authority, acceptance authority,
or release authority.

## 4. Project Orchestrator identity

The canonical Project Orchestrator identity is the `id` stored in
`.floppy/orchestrator-registry.json`. V2-04 creates no hidden second identity.

For a new V2-04 project:

`ORCH-<project_id>-00000001`

For an existing Floppy project adopting V2-04, preserve the already-current
committed Project Orchestrator ID exactly.

Generated successors use:

`ORCH-<project_id>-<8-digit-sequence>`

A generated ID may never be reused after appearing in accepted project history.
Predecessor and successor IDs remain historically distinct in the registry and
succession history.

## 6. Paired-bootstrap establishment ordering

The accepted ordering is:

1. validate the V2-03 accepted origin;
2. determine Continuity Overseer and initial Project Orchestrator identities;
3. calculate `shared_origin_sha256` from stable pre-commit origin fields;
4. establish V2-04 durable runtime linkage in the target project;
5. commit that establishment where Git applies;
6. render both prompts from that committed state;
7. make both prompts reference the same exact repository checkpoint and authority state;
8. present both prompts together for use as separate conversations;
9. preserve implementation authority and writer state unchanged.

No prompt requires a final commit SHA before that commit exists. No immutable
origin field depends on a prompt hash, and no prompt hash depends on itself.

## 7. Presence and activation semantics

- no V2-04 activation + no continuity record → lawful `V2-04 NOT ADOPTED`;
- activation `ACTIVE` + missing record → `CONTINUITY_OVERSEER_REQUIRED_RECORD_MISSING`;
- continuity record present + activation absent → `CONTINUITY_OVERSEER_UNREGISTERED_RECORD`;
- activation `ACTIVE` + valid record → lawful V2-04 active state;
- prior committed activation later removed → `CONTINUITY_OVERSEER_SILENT_DRIFT`;
- older Floppy project that never adopted V2-04 → lawful legacy state;
- V2-03 accepted state active while V2-04 absent → lawful;
- V2-04 active without lawful V2-03 accepted state → `CONTINUITY_OVERSEER_ACCEPTED_STATE_REQUIRED`.

The validator must not fabricate V2-04 state because a V2-capable source is
present. Automatic backfill and automatic migration are forbidden.

## 8. Authority fingerprint and succession

Prepared succession records calculate `authority_state_sha256` over the exact
operational authority projection:

- lifecycle state;
- active work authorization;
- active implementation authorization;
- active implementation section;
- current Section Working Model;
- repository writer;
- writer authorization reference.

Succession may not create, remove, replace, expand, or narrow authority.
If the prepared projection no longer equals current repository-backed state,
succession stops with stale-handoff behavior and must be prepared again.

At most one Project Orchestrator may be `ACTIVE`.

If a predecessor conversation is unavailable, recovery succession reconstructs
only repository-backed accepted state, lifecycle, registry, authorization,
handoff/evidence, and checkpoint facts. Missing conversation-only facts are not
invented.

## 9. Scope-drift boundary

V2-04 preserves three separate cases:

1. ordinary implementation adaptation inside accepted outcome/scope/constraints;
2. a lawful administrator-accepted V2-03 project-level revision;
3. material project-goal/fundamental-scope drift without lawful revision, which
   produces `SCOPE_DRIFT_REVIEW_REQUIRED`.

The Continuity Overseer may surface the conflict and relevant evidence. It may
not silently revise accepted project state.
