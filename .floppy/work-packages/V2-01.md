## 1. Purpose

V2-01 establishes the exact architectural and compatibility contract between the completed Floppy v1 system and Floppy v2 before later V2 capabilities are implemented.

V2-01 shall not redesign v1. It shall determine which v1 mechanisms remain authoritative and unchanged, which V2 extensions are required, how those extensions coexist with v1 state, and how tooling can distinguish and correctly process compatible lifecycle/schema/profile combinations.

V2-01 is subordinate to the accepted five-package V2 Project Plan and may not silently expand, replace, or repartition that roadmap.

## 2. Controlling principle

**Context loss is not authority to reconstruct accepted work.**

Repository-backed accepted state remains authoritative until changed through an explicit lawful revision or supersession mechanism. A newer model, schema, provider, tool version, or V2 capability does not gain authority to rewrite accepted V1 state merely because it can read that state differently.

## 5. V1 findings that constrain V2-01

- Existing V1 schema evolution must not be assumed to be a simple cumulative numeric chain. The `1.1.0` verification-only extension and `1.2.0` final-closure extension require explicit compatibility/profile reasoning.
- V1 historical schemas and accepted records remain immutable unless a lawful compatibility mechanism explicitly says otherwise.
- Reading or validating V1 state is not equivalent to migrating that project to V2.
- Root V2 development `.floppy/` state and reusable `project-seed/.floppy/` have different roles; root development control state must remain out of clean reusable `main`.
- Existing portable BCE export integrity remains accepted and should be extended only where V2 compatibility/profile identification proves necessary.
- Existing source/package inventory behavior remains accepted; new canonical V2 artifacts require deliberate package/profile impact analysis.
- Historical provisioning substitution tokens must not be misclassified as current V2 version defects.

## 7. Schema/version alternatives to resolve during V2-01

### Alternative A — V2 compatibility family

Introduce an explicit `2.0.0` compatibility/profile family while preserving V1 `1.x` schemas unchanged; require explicit profile resolution and prohibit numeric latest-version inference.

### Alternative B — continued 1.x evolution

Extend the existing family with a new `1.x` revision while introducing explicit compatibility semantics sufficient to handle existing non-cumulative extensions.

### Alternative C — component-schema composition

Maintain independently versioned component contracts and bind them through an explicit compatibility profile.

Acceptance of this work package does **not** select any alternative. Selection and proof are V2-01 implementation results.

V2-01 implementation must prove at minimum:

1. Existing accepted V1 fixtures/state continue to validate under their applicable V1 contracts.
2. V2 compatibility/profile resolution is deterministic.
3. Unsupported or ambiguous profile combinations fail safely instead of being guessed.
4. V1 projects are not silently migrated.
5. Historical accepted state remains unchanged.
6. Existing V1 lifecycle and authority invariants remain valid.
7. New schema/profile contracts validate representative positive and negative fixtures.
8. Existing repository regression tests remain passing unless an explicitly accepted compatibility change requires a documented test revision.
9. Source/package validation accounts for every new canonical V2 artifact introduced by V2-01.
10. Root development `.floppy/` remains excluded from reusable-source integration.

Exact commands, exact path scope, exact commit sequence, and exact evidence requirements are to be frozen in the separate activation/implementation package.

## 10. Compatibility risks to control

V2-01 must prevent:

- numeric “latest schema wins” behavior;
- in-place modification of V1 historical schemas;
- silent V1-to-V2 conversion;
- reconstruction of accepted state after model/context loss;
- implicit authority acquisition by the Continuity Overseer;
- implicit repository-writer acquisition by an orchestrator;
- backward-incompatible registry changes without an explicit contract;
- source/package inventories silently omitting new normative artifacts;
- portable-export consumers misreading unknown V2 records;
- reopening finally-closed V1 projects;
- treating the Official Project Plan as execution authorization;
- provider-specific documentation redefining Floppy authority; and
- conversation memory overriding repository-backed accepted evidence.

## 11. Explicit non-goals

V2-01 shall not implement:

- V2-02 provider/user onboarding or provider-specific public guides;
- V2-03 accepted-state enforcement;
- V2-04 Continuity Overseer runtime behavior or orchestrator succession implementation;
- V2-05 Official Project Plan generation, final integration, or release;
- automatic V1 migration;
- a rewrite of V1 history;
- a V2-06 work package;
- a Windows GUI, executable, desktop application, or installer; or
- root development `.floppy/` integration into reusable `main`.
